# Epoch Ledger

**Who pays for NEAR's security?** A long-term investment thesis for NEAR, with the evidence measured from block headers and a model anyone can re-run.

Built at NEAR HACKATHON (November 2026) for the **Investment Thesis** track.

- Thesis: [THESIS.md](THESIS.md)
- Live numbers and every claim with its test: [RESULTS.md](RESULTS.md)
- Dashboard, hosted: https://epoch-ledger.pages.dev (the same file as `docs/index.html`, which also opens from disk)

## What it is

NEAR mints new tokens every epoch to pay validators. A holder gets that dilution back in two ways only: gas fees that are burnt, and NEAR bought on the market with revenue captured from NEAR Intents.

Epoch Ledger measures all three flows and reduces the long-term case for NEAR to one number: how much Intents volume it takes for burn plus buyback to equal issuance.

What is measured from chain, with no indexer and no API key:

| Quantity | How |
| --- | --- |
| NEAR minted per epoch | `total_supply` in the first block header of an epoch, minus the last header of the epoch before |
| NEAR burnt per epoch | `total_supply` in the first header of an epoch, minus the last header of the same epoch |
| Stake, validator count, concentration | `validators` RPC at one block a week |
| Yield a staker actually received | share price of `linear-protocol.near` and `meta-pool.near` at one block a week |
| Balance of the Intents revenue accounts | `view_account` at one block a week |

What comes from third parties, and is labelled as such wherever it appears: NEAR/USD price, transactions and active accounts (NearBlocks), and NEAR Intents volume, fees and captured revenue (DefiLlama).

## Try it

Needs Python 3.9 or newer. No packages to install, no keys, no accounts.

**1. Rebuild everything from the committed data (10 seconds, no network).**

```
python run.py --offline
```

See: 15 lines starting `PASS`, six kill criteria with their status, then `All 15 claims hold.` The command rewrites `RESULTS.md`, `THESIS.md`, the Results block above, `data/derived/*` and `docs/index.html`. Run `git status` afterwards: nothing has changed, because the committed outputs are exactly what the committed raw data produces.

**2. Open the dashboard.**

Open `docs/index.html` in a browser. See: six headline numbers, six charts (each with its takeaway, the query behind it and a data table), a model with four sliders, the claims table and the kill criteria. The "Break-even volume" tile shows the break-even volume from RESULTS.md, rounded to the million. Move the "Intents volume per day" slider to the right until it reads that figure: "Issuance offset" reaches 100% and "Net dilution" reaches 0%.

**3. Run the tests.**

```
python -m unittest discover -s tests -v
```

See: the model formulas checked against numbers worked by hand, the epoch arithmetic checked on a three-epoch chain, the revenue account comparison checked on a two-sample case, and the committed snapshot reproduced. One test is skipped because it needs the network; step 5 runs it.

**4. Pull fresh data from mainnet.**

```
python run.py
```

See: the walk fetches only the epochs that are newer than the committed snapshot (a minute or two), re-pulls the third-party series, and rebuilds everything. Numbers move with the chain; the claims are re-tested against the new data and the run exits with code 1 if one stops holding.

To rebuild the chain data from nothing, delete `data/raw/epochs.csv` and `data/raw/samples.csv` first. The free public endpoints allow about one request a second, so a full walk to genesis takes a few hours. `python run.py --since 2025-10-01` bounds how far back it goes.

**5. Check the identity the ledger rests on, against the live chain.**

```
LIVE=1 python -m unittest tests.test_live_identity -v
```

On Windows PowerShell: `$env:LIVE=1; python -m unittest tests.test_live_identity -v`

See: for consecutive blocks inside an epoch, `total_supply` falls by exactly the `balance_burnt` of the chunks in the newer block, to the yoctoNEAR.

## How the chain walk works

The id of a NEAR epoch is the hash of the last block of the epoch two before it. So in any block header, `next_epoch_id` is the hash of the last block of the previous epoch. Following that pointer from the chain tip visits every epoch with one request each.

Validator rewards are minted in the first block of an epoch. Inside an epoch the supply only falls, by the fees burnt in each block. For epoch `e`, with `F(e)` its first block and `L(e)` its last:

```
minted(e) = supply(F(e)) - supply(L(e-1)) + burnt_in(F(e))
burnt(e)  = supply(F(e)) - supply(L(e))   + burnt_in(F(e))
```

`burnt_in(F(e))` is the sum of `balance_burnt` over the chunks included in that block. The code is [ledger/epochs.py](ledger/epochs.py).

## The model

[ledger/model.py](ledger/model.py) is four pure functions:

```
issuance_near_per_day = supply * issuance_rate / 365.25
buyback_near_per_day  = intents_volume_usd_per_day * capture_rate / price
coverage              = (burn_near_per_day + buyback_near_per_day) / issuance_near_per_day
breakeven_volume      = (issuance_near_per_day - burn_near_per_day) * price / capture_rate
```

Issuance is fixed in NEAR and the buyback is fixed in dollars, so a higher NEAR price lowers coverage. The dashboard runs the same formulas in the browser.

## Data sources

| Source | Used for | Endpoint |
| --- | --- | --- |
| NEAR archival RPC (FastNEAR, Tatum) | block headers, validators, view calls | `archival-rpc.mainnet.fastnear.com`, `near-mainnet.gateway.tatum.io` |
| neardata.xyz (FastNEAR) | block headers by height | `mainnet.neardata.xyz/v0/block/{height}/headers` |
| NearBlocks | price, transactions, active accounts, fees paid | `api.nearblocks.io/v1/charts` |
| DefiLlama | Intents volume, fees, revenue; gas fees; stablecoins; TVL | `api.llama.fi/summary/...` (URLs in `data/raw/MANIFEST.json`) |

NEAR BigQuery and the NEAR Intents Explorer API were not used: both need credentials, and this project is meant to run for anyone with nothing but Python.

## Limits

- The buyback series is DefiLlama's reading of NEAR's revenue accounts. This project checks it against the on-chain NEAR balance of those accounts (claim C15, table in RESULTS.md) but does not re-derive it trade by trade.
- Bought NEAR is held, not burnt. It lowers float, not `total_supply`.
- Intents volume is not measured from chain here.
- USD values use one daily price per day.
- This is research, not investment advice.
